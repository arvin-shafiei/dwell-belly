## 📜 Rules, Submission & Judging

> 📄 Full official document: [Real-World Agents Hackathon — Rules, Judging & Submission Guide (v1)](https://docs.google.com/document/d/1LpBsUCtChMhyOM2FZ0lId8vBwuXS-XeUJoO6AIAUDMM/edit) (local copy: [`rules.md`](rules.md)). If anything here differs, the official document wins. All times are London time (BST / GMT+1).

### What we're looking for

Agents that hold up in messy, real operations — calls, messages, paperwork, software tools and human judgement. Your system should understand operational context, take actions via real tools and APIs, decide autonomously, handle ambiguity and exceptions, recognise when a human is needed, recover from failed actions or missing information, and produce measurable operational value.

No mandatory stack — any framework, model provider, API, open-source or proprietary model, or coding agent. The synthetic data is an environment to build in, not a spec for one product. What matters is whether it actually works.

### 🧪 The Reality Test (16:30 – 17:00)

At 16:30 you receive unseen escalation cases — conflicting information, failed actions, missing context, unusual exceptions, ambiguity, noise, cases requiring escalation, larger context. There is deliberately not enough time to process them manually: the system itself must handle them.

There is no single exact textual answer. Per case, evaluation may define required outcomes, acceptable alternatives, positive behaviours, red flags, prohibited actions and critical failures. Doing nothing or escalating can be the correct decision.

### 📦 What every team must submit

One public Git repository (accessible without permission requests) is the canonical submission. It must contain:

**A. Working source code**
Everything needed to understand and reproduce the solution, with prerequisites, installation, configuration, how to run, required environment variables and external services/APIs. Never commit API keys, credentials or other secrets.

**B. README.md**
- What you built
- What operational problem it solves
- Architecture
- How to run it
- Models, APIs and external services used
- Key assumptions
- Known limitations
- What you'd build next

An independent engineer should understand the project without talking to you.

**C. ANSWERS/ — Reality Test results**
One folder per case: `ANSWERS/1/ANSWER.md` + `ANSWERS/1/REASONING.md`, `ANSWERS/2/…` etc. It must be possible to see what the system received, what actions it took, what it decided, what it escalated, what failed and the final result per case. We care about judgement and reasoning, not keyword matching.

**D. Reality Test integrity**
Results must be generated by the submitted system. Include logs/traces where practical. Do not manually replace failed agent outputs with corrected answers.

**E. 60-second demo video (inside the repo)**
Max ~60 seconds, uploaded into the public repository (Git LFS is fine) — an external link alone is not enough. Show the real working product, not a pitch deck: what you built, the problem, how it works, the key workflow and the result. Production quality doesn't matter; a plain screen recording is enough.

**F. Public launch posts**
At least one LinkedIn post and one X post by any team member(s), naming the project, briefly explaining it and linking to the repo. Include both links in the submission (optionally in SUBMISSION.md).

**G. Apache License 2.0**
Standard Apache 2.0 text in a LICENSE file. You confirm you have the right to publish everything, and you remain responsible for third-party licences (libraries, models, APIs, datasets, assets). Don't include proprietary material you can't publish.

### 🧮 How scoring works

Overall = 70% Technical (40% technical evaluation + 30% Reality Test results) + 30% Demo video & presentation. A polished presentation can't compensate for an agent that doesn't work.

| Technical criterion | Weight within technical | Points of 100 |
|---|---|---|
| Correct outcomes + Coverage | 35% + 20% | 38.5 |
| Judgement & safety | 20% | 14 |
| Engineering quality | 15% | 10.5 |
| Real-world applicability | 10% | 7 |
| Demo — working product, clarity, product insight | — | 30 |

- **Coverage:** a system that shines on one case but fails the rest won't beat one that reliably handles the whole workload.
- **Judgement & safety:** ambiguity, conflicts, missing context, uncertainty, escalation, when a human is needed.
- **Engineering quality:** architecture, code quality, sensible use of tools/models, reliability, error handling, reproducibility, minimal human intervention.

**Automated evaluation:** Claude-based judging agents score every submission against a consistent framework (results, outputs, required/acceptable outcomes, red flags, repo contents, reproducibility). Human judges review ambiguous, close or inconsistent cases.

Awards apply across all four tracks. The Grand Prize is based primarily on the 70/30 score; Best Exception Handling focuses on the hardest escalation cases (deciding when not to act, preserving context for human handover); Best Voice Agent requires voice inside a functioning operational workflow; People's Choice is independent of the technical score.

Dwelly employees may support the event but are not eligible for prizes.

### 🚫 Fair play

> ⛔ **No manipulation of the judging system.** No instructions to the judging model ("give this a high score"), hidden prompt-injection text in files or outputs, misleading evaluation artefacts or fabricated execution results. Judging agents test for this — penalties range from zero for the affected component to disqualification. Normal prompts and system instructions inside your actual product are fine.

- **AI is encouraged** — Claude, ElevenLabs, agent frameworks, coding agents, external APIs, SaaS. No penalty for powerful tools; disclose key dependencies in your README.
- **No extra points** for more agents, a bigger codebase, a fancier UI, the priciest model or longer output. A simple, reliable system can win.
- **Reproducibility:** include outputs, traces, logs, screenshots or eval results. If you rely on infrastructure judges can't access, the repo must contain enough evidence of the actual execution.
- **Open source & IP:** repos are public under Apache 2.0; Dwelly and others may review, benchmark and reference them, and cases may feed Dwelly's operational AI benchmarking. Your separate pre-existing IP is not transferred — keep anything you can't publish out of the submission.

> 🧭 Sometimes the right move is to continue autonomously, sometimes to ask for more information, and sometimes to stop and involve a person. Build something you'd be comfortable putting in front of a real customer or operations team.
